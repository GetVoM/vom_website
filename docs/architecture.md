# Architecture decisions

Status: proposed on 2026-10-25, to be confirmed with the owner before implementation. Each decision names the alternative it rejected. Technical facts about Next.js 16 come from `docs/research/next16-digest.md`.

## 1. Rendering: fully static, revalidated by tag

Every public page is prerendered. Content reads sit behind `'use cache'` with `cacheLife('max')` and tags (`pages`, `posts`, `post-<slug>`, `sectors`, `templates`, `tools`). Marketing and blog layouts export `ensureStatic = 'navigation'` so the build fails if anything makes a page dynamic by accident. Posts, news, templates, categories and authors come from Supabase (§13) through `lib/content/posts/`, tagged `posts`, `post-<id>`, `categories`, `category-<id>` and `authors`. The admin's save and publish actions expire those tags with `updateTag`, so a published change shows without a redeploy; scripts use the secret-protected Route Handler `/api/revalidate`, which calls `revalidateTag(tag, 'max')`. A post published after the last build is rendered on first request and cached. Only `/admin` and `/api` render per request; `proxy.ts` matches `/admin` alone, so public pages never pass through it.

Rejected: request-time rendering with a CDN in front. It would cost Core Web Vitals and complicate hreflang-correct caching for no benefit on a content site.

## 2. Locales: Arabic at `/`, English at `/en`, no automatic redirects

Routes live under `app/[lang]/` with `generateStaticParams` returning `ar` and `en`. `next.config.ts` rewrites `/` and every non-`/en` path to `/ar/...` (`beforeFiles`), and permanently redirects any literal `/ar/...` request to the unprefixed path. The locale is read with `next/root-params`, never from `params` at the top of a layout. There is no `Accept-Language` redirect: search engines and users get exactly the URL they asked for; the header offers the language switch, which points at the hreflang twin of the current page.

Rejected: two separate route trees (`app/(ar)` and `app/en`): duplicates every layout and loses the shared root param. Rejected: locale detection in `proxy.ts`: it hides pages from crawlers and splits caches.

## 3. URLs: preserve first, restructure later

`trailingSlash: true` so WordPress paths resolve byte-for-byte. A catch-all route `app/[lang]/[...slug]/page.tsx` resolves any preserved path through the content layer's URL index (posts under `/<category>/<arabic-slug>/`, sector pages under `/<arabic-slug>/`, e-invoicing guides under `/الفوترة-الإلكترونية/<slug>/`, templates under `/templates/<slug>/`). Dedicated routes exist only for pages whose structure is new (home, pricing, features, about, contact, blog index, category archives) and for the tools: `app/[lang]/tools/page.tsx` and `app/[lang]/tools/[slug]/page.tsx` (2026-11-12, Arabic only, English 404s), kept out of the catch-all so the calculators' client code stays off every other page it serves. The English ZATCA Phase 2 page has its own route too, `app/[lang]/zatca-e-invoicing-phase-2/page.tsx` (2026-11-12, English only, the Arabic path 404s), for the same reason: its lead form is client code. Its Arabic twin is the e-invoicing hub (`zatcaPhase2Paths` in `lib/i18n/routes.ts`): the navbar item, the language switch and the hreflang pair use that pair, and the sitemap lists the two together. The VoM Pay result pages have their own routes in both languages, `app/[lang]/vom-pay-success/` and `app/[lang]/vom-pay-failure/` (2026-11-12): the app sends payers to `/vom-pay-*/` and `/en/vom-pay-*/`, so those exact addresses must keep answering, each in its own language, `noindex` and out of the sitemap. The failure page reads the app's `?vom_pay_errors=<code>` in the browser (`components/vompay/PayError.tsx`, `lib/leads/vom-pay.ts`), so the page stays static; the query survives the missing-slash 308 and the `/ar/` 301. Redirects for the `redirect` and `retire` rows of `docs/content/url-map.csv` go in `next.config.ts` `redirects()` with `statusCode: 301` (about 25 entries) and a small `410` handler.

Paid-campaign landing pages live under their own root layout, `app/(campaigns)/` (2026-11-12), beside the admin's: no site header, navigation or footer, Arabic only, `noindex, follow`, out of the sitemap. Each page's path is excluded from the Arabic rewrite in `next.config.ts` (`ARABIC_PATH`), so `/<page>/` is served directly, `/ar/<page>/` still 301s to it and `/en/<page>/` 404s through the catch-all. The first is `/digital-ads-2023-landing-page/` (`components/campaigns/`, content in `lib/content/campaigns/`).

Rejected for launch: moving posts to `/blog/<slug>/`. It is cleaner but adds about 230 redirects and temporary ranking volatility during a migration that already changes platform, design and markup. It can be done later as its own change with its own redirect map.

## 4. Content layer: one interface, swappable storage

`lib/content/` exposes typed functions (`getPage(path, lang)`, `getPost(slug)`, `listPosts({ category, page })`, `getSector(slug, lang)`, `listTemplates()`, `getTool(slug)`, `getAuthor(slug)`, `getUrlIndex()`), each cached with `'use cache'`. The first implementation reads MDX files with frontmatter from `content/` (imported from WordPress by a one-off script that pulls the REST API, converts HTML to MDX, downloads media to `public/media/`, and strips editor artefacts such as `data-start` attributes). A later CMS plugs in behind the same interface. Pages never import from `content/` directly.

Why MDX first: the owner deferred the CMS decision; MDX needs no service, keeps Git history, and lets Claude Code edit content. The import script is kept so the migration is repeatable. First in place (2026-11-10): the e-invoicing hub and guides, through `@next/mdx` (bodies loaded by dynamic import in `lib/content/einvoicing/`, house components mapped in the root `mdx-components.tsx`, `remark-gfm` named as a string for Turbopack). Metadata lives in a typed catalogue (`lib/content/einvoicing/catalogue.ts`) rather than frontmatter, and the import read the saved WordPress HTML (`scripts/import-einvoicing.mjs`) rather than the REST API. Long-form pages exceed the 100 KB HTML budget because the RSC payload repeats every word (130–238 KiB raw, 26–45 KiB gzipped); the template's own markup is kept lean. The features page (2026-11-10) is the same case at 134 KB Arabic / 120 KB English raw (23 / 21 KB gzipped): its register rows carry no per-cell classes, CSS counters draw every entry number, and its images carry their display width so each srcset holds only 1x and 2x. The site chrome (header with mega menus, footer, their RSC) is already about 90 KB on every page.

Since 2026-11-11 posts and news are not MDX. They live in Supabase and are edited in the site's own admin at `/admin` (§13): `lib/content/posts/` exposes `getPostByPath`, `listPosts`, `listCategories`, `getCategory`, `getAuthor`, `postPaths` and `relatedPosts`. Bodies are stored twice, as the editor's document and as HTML rendered from it on the server; one schema (`lib/editor/extensions.ts`) is shared by the editor, the save action and `scripts/import-wordpress.mjs`. The catch-all route resolves blog paths against one cached index of every published path, so an unknown URL is a 404 without a database query. The e-invoicing guides and the accounting guide stay on MDX.

The tools (2026-11-12) are MDX too, in code, not Supabase: metadata in `lib/content/tools/catalogue.ts`, each page split by `scripts/import-tools.mjs` into `content/tools/<id>.lead.mdx` (up to its last calculator, shown full width as the poster bands) and `content/tools/<id>.mdx` (the article), read through `lib/content/tools/`. The calculators are client components (`components/tools/calculators.tsx`, one 7 KB gzipped chunk loaded only on tool pages) over pure functions in `lib/tools/` (`calc`, `parse`, `format`, `rates`). See `docs/content/tools/`.

## 5. Metadata and structured data: generated from one source

`lib/seo/` builds `Metadata` objects and JSON-LD from content records: title templates per type, absolute canonical, `alternates.languages` from the hreflang pairs in the URL index, Open Graph with a generated image (`opengraph-image.tsx` per route type, Arabic font passed to `ImageResponse`), and JSON-LD by type (`Organization` + `WebSite` in the root layout; `SoftwareApplication` with `Offer` on home, features and pricing; `Article` with `author` and `reviewedBy` on posts and guides; `BreadcrumbList` everywhere; no `FAQPage`, since Google no longer shows FAQ rich results for sites like this one (owner, 2026-11-10); on the tools (2026-11-12), `Article` with author and reviewer, one free `WebApplication` per calculator and `BreadcrumbList`, and on the index a `CollectionPage` listing them; no `HowTo`, since Google no longer shows HowTo rich results). Sitemaps are split by type with `generateSitemaps` and listed in `robots.ts`.

## 6. Fonts: self-hosted through `next/font`, two families at most

IBM Plex is the typeface (owner, 2026-11-19; it replaced Effra): IBM Plex Sans for Latin text and every digit, IBM Plex Sans Arabic for Arabic, both from `next/font/google`, fetched at build time and served from the site as subset WOFF2. Plex Sans is one variable file (latin subset); Plex Sans Arabic is four static weights (300, 400, 500, 700, arabic subset). The stack puts Plex Sans first, so each glyph takes the first face that has it. Plex Sans carries no fallback face of its own: next/font's automatic one is a local Arial with no unicode-range, which holds Arabic glyphs and would draw every Arabic letter before Plex Sans Arabic could. Turbopack ignores `adjustFontFallback: false` and drops that face only when a `fallback` list is given, so `app/fonts.ts` passes an empty one.

## 7. Images and media

**Images are pre-optimized static files (2026-11-25); Vercel's image optimizer is off** (`images: { unoptimized: true }`), because the Hobby plan's 5,000 transformations a month ran out after launch. `pnpm optimize:images` (`scripts/optimize-images.mjs`, sharp) turns every raster in `public/` (not `og/`, `wp-content/`, or the JSON-LD logo) into WebP at quality 80 under `public/images/optimized/<same path>.webp`: twice the widest the image renders (measured in the browser across the site, `scripts/image-widths.json`), at most 2560 px, never upscaled, transparency kept, metadata stripped; images shown 480 px or wider also get `-640w` and `-1280w` copies. The originals stay where they are, so no image URL changed and no redirect was needed. `lib/images/manifest.json` records every output with a hash of its source and settings, so reruns skip what has not changed; the outputs are committed, and Vercel never runs sharp. Add an image, then run the script (and add its measured width to `image-widths.json`, or it is sized for the 1280 px container). Components import `Image` from `components/ui/Image.tsx`, never `next/image` (ESLint enforces it): it resolves the files and renders next/image for a single file, or a plain `<img srcset sizes>` (with the head preload for LCP images) when there are copies; client components get the resolved image from their server parent and render `ImageView`. `staticSrc()` (`lib/images`) picks one file for logos, cards, CSS backgrounds and the ZATCA SVG. The blog's images stay on R2: `pnpm optimize:media --upload` (`scripts/optimize-media.mjs`) adds `<name>-w640.webp` and `-w1280.webp` beside each image posts use (covers also `-w384.webp` for the lists and `<name>-og.jpg`, a JPEG share image at most 1200 px wide made from the WordPress original), never overwriting an object, and lists them in `lib/images/media-manifest.json`. Run it after publishing posts, then deploy; until then a new image is served as uploaded. Share images in `public/og/` stay PNG. Blog media lives in a Cloudflare R2 bucket served at `media.getvom.com`. The import copied every file a post uses to its WordPress key (`wp-content/uploads/YYYY/MM/<file>`), with a `<stem>.webp` beside each image (at most 1600 px wide) that the content uses. `/wp-content/uploads/:path*` on the site 301s to the same key on the media domain, and WordPress size variants (`name-300x135.jpg`) 301 to the original. Files the site still serves itself from `public/wp-content/uploads/` (the invoice templates, the e-invoicing PDF) are read at config time and left out of that redirect. New images are resized to WebP in the browser and sent straight to R2 through a five-minute presigned PUT, under `uploads/YYYY/MM/`.

## 8. Analytics and third parties

GTM `GTM-PS28X6L` via `components/analytics/GoogleTagManager.tsx` (`afterInteractive`; since 2026-11-23 its own component, because `@next/third-parties` preloaded the 180 KB container at high priority beside the CSS and fonts; gtm.js is now preloaded at low priority and the tags fire at the same moment), in the site layout and the campaign layout (installed 2026-11-12), **on the production deployment only** (`lib/seo/tags.ts`: `VERCEL_ENV === "production"`, or `GTM_ON=1` on purpose). The container's conversion triggers have no hostname condition, so a form sent from a preview or a laptop would reach Google Ads, GA4, Meta and Stape as a real lead; a local test on 2026-11-12 did exactly that before the gate existed. The container (read from its public `gtm.js` on 2026-11-12) runs GA4 `G-7EXVYN9CNW` through the Stape server container at `edge.getvom.com`, Google Ads `AW-476440452` with enhanced conversions, the Meta pixel and Stape's user-data collector. The campaign form reproduces the old Elementor form's event, `{event: "elementor_form_success", form_name: "Digital Ads 2026", form_id: "c8749cd"}`, which fires that campaign's Meta Lead, Google Ads conversion, GA4 `generate_lead` and Stape event (`lib/leads/digital-ads-2023.ts`); change the two together. The English ZATCA Phase 2 form pushes its old Elementor event too, `{event: "elementor_form_success", form_name: "Digital Ads 2023", form_id: "e52c297"}` (`lib/leads/zatca-phase-2.ts`), but no trigger listens for that id, so it fires no conversion until one is added in GTM. The old page's Google Ads user-data tag (a native submit of a form with Elementor's class) does not fire on the new form. The VoM Pay success form pushes `{event: "elementor_form_success", form_name: "VomPayForm", form_id: "619dac9"}` (`lib/leads/vom-pay.ts`); no trigger listens for it either. Web Vitals go to the dataLayer as `{event: "web_vitals", metric_name, metric_value, metric_delta, metric_id, metric_rating, navigation_type}` (`components/analytics/WebVitals.tsx`, `useReportWebVitals`, CLS ×1000, production only); a GA4 event tag on a `web_vitals` custom-event trigger in the container has to forward them, and none existed on 2026-11-23. Chat (Crisp) and help centre (Zendesk) widgets load only after the first user interaction or on the contact page. TikTok and other pixels stay inside GTM. Consent handling is a launch checklist item.

**PostHog custom events (2026-11-17).** The catalogue of event names and properties is `lib/analytics/events.ts`; add an event there before sending it. Client Components call `track()` (`lib/analytics/track.ts`). Server-rendered markup ships no tracking code: one delegated listener (`components/analytics/Tracker.tsx`, mounted in the public root layouts, not the admin) names link clicks from their address (`lib/analytics/classify.ts`: sign-up, login, demo, WhatsApp, downloads, stores, social, outbound), reads `data-track="event_name"` and `data-track-*` attributes, and hears FAQ openings and the pricing billing switch. Each of its events carries `location` (the nearest `data-track-section`, else the enclosing section's id or class) and `locale`. The lead action sends `lead_recorded` / `lead_rejected` from the server (`lib/analytics/server.ts`, `posthog-node`) on the visitor's own PostHog id, which the form posts as `ph_distinct_id`. When a lead is saved the browser calls `posthog.identify` with the normalised mobile number as the person id and the name, email and sector as person properties (owner's decision); nothing typed into a calculator or form is ever an event property. Consent for this is still the launch checklist item above.

**PostHog loading and new events (2026-11-23).** The browser SDK is the slim core with only the extension bundles the site uses (`lib/analytics/posthog.ts`: analytics, session replay, error tracking, toolbar; no surveys, flags or experiments), and `instrumentation-client.ts` imports it dynamically, so it no longer holds up hydration (initial JS on the homepage went from about 315 to 203 KB gzipped). Components reach it only through `lib/analytics/client.ts` (`withPostHog` queues calls until it has started; `startedPostHog` for reads that cannot wait); never import `posthog-js` directly. Every browser and server event carries `environment` (`production`, `preview` or `development`, from `DEPLOYMENT_ENV` in `next.config.ts`) and the browser's carry `locale`; filter on `environment = production` for visitor numbers, since laptops and previews send to the same project. `capture_dead_clicks` is on. New events: `article_read` (`components/analytics/ReadTracker.tsx`, the end of a post, news item, template or guide, with `seconds`), `page_not_found` (`components/analytics/TrackOnMount.tsx` in `NotFound`, with PostHog's `$referrer`, for finding broken inbound links after the migration), and the catalogue now lists `pricing_compare_clicked` and `pricing_features_clicked`. An admin is identified with `is_admin: true`, so the team's own visits can be filtered out.

**SEO audit fixes (2026-11-17).** `retire` rows answer 410: `next.config.ts` reads them from `url-map.csv` and rewrites each to `app/api/gone/route.ts`. `/sitemap.xml` is the sitemap index (`app/api/sitemap-index/route.ts`, behind a rewrite, because `app/sitemap.ts` owns that name as a metadata file) and the one address in `robots.txt`; `/feed/` is the blog's RSS (`app/api/feed/route.ts`), named in every page's head (`alternates.types` in `buildMetadata`); `/llms.txt` is built from the content catalogues (`app/api/llms/route.ts`, behind a rewrite) since 2026-11-23. A list with nothing in it (an author with no posts, the English news) is `noindex, follow`, out of the sitemap and not offered as a hreflang twin. Every page has a share image: its own, or `fallbackImage()` in `lib/seo/metadata.ts`. In JSON-LD, `reviewedBy` sits on a `WebPage` whose `mainEntity` is the `Article`; every person is one entity by `@id` (`/author/<slug>/#person`), including on the guides, whose bylines name their author pages (`writerSlug`, `reviewerSlug` in `lib/content/einvoicing/copy.ts`). Preview deployments send `X-Robots-Tag: noindex` and a closed `robots.txt` (`VERCEL_ENV`). PostHog goes through the reverse proxy `https://n.getvom.com` (`NEXT_PUBLIC_POSTHOG_HOST`, which the CSP is derived from). After editing Supabase content by hand, delete `.next/cache/fetch-cache` before a local build, or call `/api/revalidate` on a deployment: cached post data otherwise survives the build.

## 9. Forms and conversion

Primary CTAs link to `app.getvom.com` registration (`/ar/company-register-show`, `/en/company-register-show`) with UTM parameters. Demo booking keeps the Calendly link. Lead forms post to one Server Action, `submitLead(form, data)` (`lib/leads/`): it validates against the form's schema, verifies the Cloudflare Turnstile token, inserts into the `leads` table with the secret key (the public key cannot write there, owner 2026-11-11), then sends an optional Resend notification. The insert comes first, so an email failure never loses a lead. Each form is an entry in `lib/leads/forms.ts`, named by its page's slug, with its schema, its extra fields (saved in `payload`) and the shared fields it never collects. The first live form is the campaign page's, `digital-ads-2023-landing-page` (2026-11-12): name and a Saudi mobile required (`lib/leads/phone.ts` reads any spelling and stores `05XXXXXXXX`), email and business sector optional; the URL's `utm_*`, `gclid` and `fbclid` are saved in `utm`. The second is the English ZATCA Phase 2 page's, `zatca-e-invoicing-phase-2` (2026-11-12): name and a Saudi mobile, both required, nothing else. The third is the VoM Pay success page's, `vom-pay-success` (2026-11-12), posted from both languages (the lead's `locale` says which): name and a Saudi mobile required, email optional. Both render the one client component, `components/forms/LeadForm.tsx`, which takes the form's name, its locale, its copy, its GTM event and the optional email and sector fields, and is styled from the shared `.lead-` block in `app/globals.css`; each page dresses it from its own block. The form waits for the Turnstile token before posting, turns a failed call into a message instead of an error page, and on success pushes its page's GTM event in §8. The admin's leads page has one chip per form with its count (each registered form shows before its first lead), a date range, per-form columns, and a CSV export that gives each extra field and attribution key its own column when a form is chosen.

## 10. Security headers

Static CSP in `headers()` (no nonces, because nonce CSP forces dynamic rendering; scripts and styles therefore allow `'unsafe-inline'`), naming Turnstile, Supabase, `media.getvom.com`, the R2 upload endpoint, YouTube's no-cookie player, Google Tag Manager and the tags its container fires (Google Ads and GA4, the Stape server container at `edge.getvom.com`, the Meta pixel, Stape's scripts; `'unsafe-eval'` for the container's Custom JavaScript variables). Left blocked on purpose: the Meta template's helper script from the public npm CDNs and the Meta pixel's calls to `*.run.app` and `*.on.aws` hosts; HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors`.

## 13. Backend services (blog, admin, leads)

Decided by the owner on 2026-11-11; the full design is `docs/superpowers/specs/2026-11-11-blog-backend.md`. It replaces "MDX first, CMS later" for posts and news; the e-invoicing guides and the accounting guide stay on MDX.

- **Supabase** (free plan): project `vom-website`, ref `miwhkjcqhmebeojlqlqm`, region `eu-central-1` (Frankfurt), Postgres 17, in the GetVoM organisation. It holds posts, categories, authors, leads and the admin allowlist, and Supabase Auth signs admins in. Migrations live in `supabase/migrations/` and are applied through the Supabase MCP; `lib/supabase/types.ts` is regenerated after each one. Row level security is on for every table: the public key reads published posts, categories and authors and may add a lead; everything else needs a user on the `admins` list.
- **Vercel functions** are pinned to `fra1` in `vercel.json`, beside the database.
- **Cloudflare R2** serves media at `media.getvom.com`; a second private bucket keeps database backups.
- **Cloudflare Turnstile** protects public forms.
- **Admin** at `/admin` by default, under its own root layout outside `app/[lang]`, never indexed. The private variable `ADMIN_PATH` moves it to `/<ADMIN_PATH>/` and makes `/admin` a 404 (rewrites in `next.config.ts`; `lib/admin/path.ts` builds every admin link; the value reaches client components through a provider, never a `NEXT_PUBLIC_` variable, and is not named in `robots.txt`). Supabase Auth with email and password, public sign-ups off. Every page and action checks the session and the `admins` list on the server (`lib/admin/auth.ts`); the panel's layout renders nothing, not even its menu, before that check passes. `proxy.ts` only keeps the session fresh: it runs for requests carrying the `vom_admin` cookie that signing in sets, so the public never passes through it. The editor is Tiptap on one schema (`lib/editor/extensions.ts`) with a full toolbar, image upload by picking, dropping or pasting, an HTML view and full screen. Content types: posts, news and templates.
- **Free-plan safety**: `.github/workflows/supabase-keepalive.yml` reads one row daily so the project is not paused; `supabase-backup.yml` dumps the database weekly into the private backup bucket and keeps eight.
- **Checks**: `node scripts/check-blog-urls.mjs` asserts every post, news and category row of `url-map.csv` against a running site.
